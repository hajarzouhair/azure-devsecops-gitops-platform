# Demo Scenarios — Kubernetes Incident Investigator

This document presents two deliberately triggered incident scenarios designed to demonstrate the capabilities of the **Kubernetes Incident Investigator**.

The scenarios cover two complementary categories:

- **Scenario 1 — Readiness Probe Investigation**: investigation of a Kubernetes runtime incident directly on AKS.
- **Scenario 2 — Vulnerability Detection and Analysis**: analysis of security findings generated by the CI/CD pipeline.

In both cases, the Agent collects data from the available tools, correlates the evidence, and produces a structured diagnosis along with remediation recommendations.

> **Safety boundary:** The Agent is configured as an investigation and diagnostic tool. It does not modify the cluster, source code, or pipeline configuration.

---

# Scenario 1 — Readiness Probe Investigation

## Setup

A Kubernetes incident is deliberately triggered by directly modifying the `portfolio-app` Deployment in the AKS cluster.

This modification is performed directly on the cluster to simulate a real runtime incident **without modifying Git and without triggering a new CI/CD pipeline**.

The readiness probe is deliberately configured with an incorrect endpoint:

```bash
kubectl patch deployment portfolio-app -n dev --type='json' -p='[
  {"op": "replace", "path": "/spec/template/spec/containers/0/readinessProbe/httpGet/path", "value": "/actuator/health/readyz"}
]'
````

The application actually exposes:

```text
/actuator/health/readiness
```

while the probe is looking for:

```text
/actuator/health/readyz
```

The critical difference is the **final `z`** in `readyz`.

The `/actuator/health/readyz` endpoint therefore does not exist, causing the readiness probe to continuously fail.

### Expected behavior

The Pod remains:

```text
Running
```

but is not considered:

```text
Ready
```

Kubernetes therefore removes the Pod from the Service endpoints.

The problem is particularly important in this scenario because the application has only one replica (the replica count was reduced to 1 because of a maximum pod limit of 30 encountered on the system node). The absence of a Ready Pod therefore results in **complete application traffic unavailability**.

---

**Evidence collection and correlation.**

The Agent does not rely on a single information source. It cross-correlates multiple independent sources to build its diagnosis.

The calls performed allow it to retrieve, among other things:

* the list of Pods using **`pods list`**;
* Kubernetes events using **`events_list`**;
* the Deployment configuration using **`resources_get Deployment`**;
* application logs using **`pods_log`**;
* Prometheus metrics using **`prometheus execute_query`**.

This correlation of five sources allows the Agent to distinguish the **symptom** from the **actual root cause**.

## Agent's Final Response

![Agent's Final Response](/ai-agent/docs/images/response1.png)

### Correction

Restore the correct probe configuration:

```text
/actuator/health/readiness
```

Then verify:

```bash
kubectl get pods -n dev
kubectl get endpoints -n dev portfolio-app
```

The Pod should become `Ready` again and reappear in the Service endpoints.

# Scenario 2 — Vulnerability Detection and Analysis

## Setup

The second scenario simulates a security incident detected during the CI/CD pipeline.

Trivy analyzes the application image and its dependencies and detects several findings, including three **CRITICAL** vulnerabilities affecting the Apache Tomcat dependency.

In a normal DevSecOps pipeline, these findings should trigger the **security gate** and prevent the pipeline from proceeding to subsequent stages.

To allow the Agent demonstration and generate an actionable analysis report, the blocking behavior was temporarily disabled using:

```bash
  script:
    - trivy image --format json --output trivy-report.json --input image.tar
    - trivy image --exit-code 1 --severity HIGH,CRITICAL --input image.tar || true
    - echo "Trivy scan completed"
```

This modification is **for demonstration purposes only**.

> **Important:** `|| true` neutralizes the scan's exit code and therefore disables the safeguard that would normally cause the job to fail. This configuration must not be kept in a production pipeline.

The scan produces, among other results:

| Target                      | Type   | Vulnerabilities | Secrets |
| --------------------------- | ------ | --------------: | ------: |
| `image.tar (alpine 3.24.1)` | alpine |               0 |       - |
| `app/app.jar`               | jar    |               3 |       - |

The three findings have **CRITICAL** severity:

```text
Total: 3
HIGH: 0
CRITICAL: 3
```

**Findings produced by Trivy.**

The scan identifies three critical vulnerabilities in:

```text
org.apache.tomcat.embed:tomcat-embed-core
```

Installed version:

```text
10.1.55
```

Detected vulnerabilities:

| CVE              | Severity | Description                                                             |
| ---------------- | -------- | ----------------------------------------------------------------------- |
| `CVE-2026-65182` | CRITICAL | Security constraint bypass due to improper access control               |
| `CVE-2026-65905` | CRITICAL | Authentication bypass via limited replay attack in DIGEST authenticator |
| `CVE-2026-68525` | CRITICAL | Unauthorized resource access via FORM authentication bypass             |

Trivy indicates the following fixed versions, among others:

```text
10.1.58
11.0.25
9.0.121
```

for the corresponding release branches.

The scan also indicates that no vulnerabilities were detected in the analyzed Alpine target:

```text
image.tar (alpine 3.24.1) → 0 vulnerabilities
```

---

## Analysis Produced by the Agent

### 1. CRITICAL Vulnerabilities

The Agent identifies the three CVEs affecting `tomcat-embed-core:10.1.55`.

The potential risk includes:

* bypassing access controls;
* bypassing authentication mechanisms;
* unauthorized access to protected resources.

The Agent therefore recommends treating these findings as **blocking issues before production deployment**.

### 2. SAST Findings

The analysis also identifies a **Medium**-severity SAST finding:

```text
Allocation of resources without limits or throttling
```

Location:

```text
ci/ai_security_review.py:70
```

The Agent interprets this as a potential risk of excessive resource consumption and denial of service.

It correctly distinguishes this finding from the Tomcat vulnerabilities: both issues belong to the broader security context but have different technical root causes.

### 3. SBOM Analysis

The Agent also examines the components present in the image and identifies, among others:

```text
Alpine 3.24.1
JDK 21.0.12
Jackson 2.21.4
gnutls 3.8.13
BusyBox 1.37
```

It does not present these components as vulnerable when no corresponding finding is provided.

Instead, it uses them to identify security considerations and potential attack-surface reduction opportunities.

### 4. Correlation

The Agent correlates the different layers:

```text
CI/CD
  │
  ├── Trivy
  │     └── 3 CRITICAL Tomcat
  │
  ├── SAST
  │     └── resource limits / throttling
  │
  └── SBOM
        └── image composition
```

This correlation enables the Agent to produce a more comprehensive analysis than a simple CVE listing.

## Agent's Final Response

![Agent's Final Response](/ai-agent/docs/images/response2.png)

**Final report generated by the Agent.**

[Final report generated by the Agent](/ai-agent/ai-security-report.md)

The Agent structures its response into several levels:

1. executive summary;
2. CRITICAL vulnerabilities;
3. HIGH vulnerabilities;
4. SAST findings;
5. SBOM analysis;
6. findings correlation;
7. key risks;
8. remediation actions;
9. deployment recommendation.

### Main Recommendation

The Agent recommends **not deploying to production** until the vulnerable Tomcat dependency has been upgraded to a fixed version.

It specifically recommends:

* upgrading `tomcat-embed-core`;
* reviewing the authentication configuration;
* adding security regression tests;
* replacing `SNAPSHOT` versions with pinned versions;
* reducing the image attack surface;
* re-enabling a CI security gate for critical findings;
* running Trivy and SAST again after remediation.

### Non-Intervention Principle

The Agent explicitly states that its actions are **suggestions only**:

```text
Note: suggestions only; no modifications are performed.
```

It therefore modifies neither the code, nor the pipeline, nor the image, nor the infrastructure.

# Demo Summary

The two scenarios demonstrate two different capabilities of the Kubernetes Incident Investigator:

| Scenario            | Domain             | Incident                     | Sources Analyzed                           | Result                          |
| ------------------- | ------------------ | ---------------------------- | ------------------------------------------ | ------------------------------- |
| 1 — Readiness Probe | Kubernetes Runtime | Incorrect HTTP probe         | Pods, Events, Deployment, Logs, Prometheus | Root cause + blast radius + fix |
| 2 — Vulnerabilities | DevSecOps / CI     | Vulnerable Tomcat dependency | Trivy, SAST, SBOM                          | Risk analysis + remediation     |

### Scenario 1 — Runtime Investigation

The Agent demonstrates its ability to:

* query the cluster directly;
* correlate multiple independent sources;
* cite the evidence associated with each statement;
* distinguish symptoms from the root cause;
* analyze the blast radius;
* propose multiple remediation options;
* respect the non-intervention principle.

### Scenario 2 — Security Analysis

The Agent demonstrates its ability to:

* analyze Trivy results;
* identify critical vulnerabilities;
* contextualize their impact;
* correlate Trivy, SAST, and SBOM data;
* prioritize risks;
* propose remediation actions;
* recommend blocking a deployment containing critical vulnerabilities.

These two demonstrations therefore illustrate two complementary roles of the Agent:

```text
                    Kubernetes Incident Investigator
                                  │
                  ┌───────────────┴────────────────┐
                  │                                │
                  ▼                                ▼
        Runtime Investigation              Security Analysis
                  │                                │
            AKS / Kubernetes                  CI/CD / Trivy
                  │                                │
        Pods / Events / Logs             CVE / SAST / SBOM
                  │                                │
                  └──────────────┬─────────────────┘
                                 ▼
                      Evidence-based diagnosis
                                 │
                                 ▼
                         Remediation guidance
```

The Agent therefore acts as an **investigation and correlation layer** on top of the operational and security tools already present in the DevSecOps platform.
